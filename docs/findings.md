# 自动恢复机制与实测记录

本记录来自 2026-11-14 一台 Windows 机器上的 aTrust + EAIO 安装环境。具体任务、服务及日志线索如下。

验证环境为 Windows 11 专业版 x64（10.0.26300）。文件版本分别为 `aTrustAgent.exe 2.5.16.31`、`aTrustTray.exe 2.0.2.0`、`eaio_service.exe 16.42.1907`；这些是组件文件版本，不代表统一的客户端安装包版本。

| 入口 | 观察到的配置或行为 | 按需模式的处理 |
| --- | --- | --- |
| `\aTrustDaemonGuarder` | SYSTEM 执行 `aTrustServRepair.exe --start-aTrustService`；每五分钟及登录时触发 | 禁用并停止正在运行的任务 |
| `\eaio_watchdog_daily` | SYSTEM 每五分钟执行 `eaio_watchdog.exe` | 禁用并停止正在运行的任务 |
| 两项服务的失败恢复 | 三次恢复动作均为三秒后重启服务 | 将恢复动作设为无操作 |
| 当前用户 `Run\aTrustTray` | 登录时启动客户端 | 备份后删除这一项 |
| aTrust 主服务内部守护 | 服务运行时再次创建代理、隧道子进程 | 先停主服务，再核实并清理残留进程 |

主任务对应的完整命令：

```text
"C:\Program Files (x86)\Sangfor\aTrust\aTrustAgent\aTrustServRepair.exe" --start-aTrustService
```

服务启动方式已成功设为手动，随后系统事件 7040 显示 SYSTEM 将它改回自动；同一时段客户端服务日志记录服务重新启动，任务触发时间与恢复吻合。任务动作明确负责启动主服务。7040 记录本身不包含调用程序的 PID，因此“由该修复任务改回启动方式”是结合任务定义及时间关系作出的归因，尚无调用进程审计记录直接证明这一点。

EAIO 服务不接受普通 STOP 控制。退出流程先关闭恢复入口，再核实实际程序路径，通过同一进程句柄结束该服务进程，随后清理两个安装目录下的其他运行程序。仅杀死托盘或隧道进程，无法阻止尚在运行的守护组件重新创建它们。

## 网络与退出验证

处理前，Bing、百度的直接 HTTPS 请求在 TLS 阶段中断，curl 的 HTTP 状态为 `000`（未取得 HTTP 响应）。处理后两站返回 `200`。测试使用 `--noproxy '*'` 绕过 curl 的显式代理设置，流量仍可能经过系统路由、TUN 或过滤驱动。

实际完成了“退出 → 启动 → 再退出”，退出后连续观察六分钟，每三十秒核验一次，十二次均满足：两项服务为 `Stopped / Manual`、两项保活任务保持禁用、两个安装目录内没有运行进程。已加载的网络过滤驱动保持原状。重启后的持久性尚未实测；这些结果覆盖当时的机器、安装配置和观察窗口。

## 为什么批评这些设计

按需使用意味着启动和退出都由用户决定。一个软件把手动配置反复改回自动、在退出后依靠多个入口复活，又让用户承担网络冲突的排查成本，理应受到严厉批评。

“为了你好”不能变成“由不得你”。退出后自动回来、手动设置被覆盖，这种流氓式的行为应当被产品本身修正。一个退出按钮需要外置工具才能兑现承诺，足够荒唐了。

本项目希望厂商提供真正可持续的按需模式：清楚展示全部后台组件、明确提供关闭保活的选项，并尊重用户已经作出的选择。
